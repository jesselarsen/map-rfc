 MAP Core: Message Envelope, Sessions, Negotiation, and Error Handling
                           draft-map-core-01

Abstract

   This document defines the mandatory core of the Manolito Agent
   Protocol (MAP): a signed CBOR/COSE message envelope with
   deterministic encoding, a version/suite/extension negotiation
   handshake, session establishment with transport channel binding,
   replay protection, credit-based flow control, a uniform error
   taxonomy, the extension framework, and normative bindings to libp2p,
   QUIC, TCP+TLS, and WebSocket transports.  Every other MAP document
   layers message _contents_ on the envelope defined here.

2.  Overview

   A MAP interaction has two phases.  First, peers establish a
   *session*: an encrypted, mutually authenticated transport connection
   (or logical stream) over which they exchange HELLO messages to
   negotiate a protocol version, cryptographic suite, limits, and
   extensions.  Second, they exchange *envelopes* — individually signed
   CBOR messages — whose content field is defined by the companion
   specifications.  Some envelopes (descriptors, receipts, revocations)
   also travel _out of session_ via DHT storage or gossip; the envelope
   format is identical, but channel binding is absent and replay rules
   differ (§7.4).

   Design invariants (rationale in 01-design-critique.md C2, C4):

   *  I1: Signatures cover the exact transmitted bytes.  Verifiers MUST
      NOT

   re-serialize before verifying.

   *  I2: Every envelope is independently verifiable given only the
      sender's

   key material (self-contained authentication).

   *  I3: Unknown non-critical fields are ignored _and preserved
      verbatim_ when

   a message is stored or forwarded.

   *  I4: All normative structures are defined in CDDL [RFC8610] over
      the

   deterministic CBOR profile of §4.2.

5.  The Envelope

5.1.  Structure

   Every MAP message is a COSE_Sign1 [RFC9052] object, CBOR tag 18:






Larsen                   Expires 18 January 2027                [Page 4]

Internet-Draft              draft-map-core-01                  July 2026


   Envelope = #6.18([
     protected:   bstr .cbor ProtHdr,
     unprotected: {},                  ; MUST be empty map; receivers ignore
     payload:     bstr .cbor Body,
     signature:   bstr .size 64        ; per negotiated suite (Ed25519 here)
   ])

   ProtHdr = {
     1 => -8,                          ; COSE alg: EdDSA
     4 => AgentID,                     ; COSE kid: SENDER AgentID
     ? 33 => [+ bstr]                  ; x5chain-slot reused: delegation chain
   }                                   ; (identity §6); order: leaf..root

   Body = {
     0  => Version,                    ; protocol-version (negotiated, §6)
     1  => uint,                       ; msg-type (registry §11)
     2  => MsgID,
     3  => Timestamp,
     ? 4  => AgentID,                  ; recipient (REQUIRED in-session)
     ? 5  => uint,                     ; ttl-ms (store-and-forward objects)
     ? 6  => SessionID,
     ? 7  => uint,                     ; seq (REQUIRED in-session, §7.2)
     ? 8  => [* int],                  ; crit: ext keys receiver MUST grok
     ? 9  => ExtMap,                   ; extensions
     10 => any                         ; content, per msg-type
   }

   The signature is computed per COSE over Sig_structure =
   ["Signature1", protected, external_aad, payload] encoded with §4.2.
   external_aad is the channel-binding token (§7.3) for in-session
   messages and the empty byte string for out-of-session objects.

5.2.  Deterministic encoding profile

   All CBOR that is signed, hashed, or content-addressed MUST use RFC
   8949 §4.2.1 core deterministic encoding: shortest-form integers,
   definite-length strings/arrays/maps only, map keys sorted bytewise on
   their encoded form, no duplicate keys.  Floating-point values MUST
   NOT appear in signed structures; quantities that are conceptually
   fractional use integer milli-/micro-units or CBOR decimal fractions
   (tag 4) with integer mantissa and exponent.  Per invariant I1, this
   profile governs _producers_; verifiers operate on received bytes and
   additionally MUST reject envelopes violating the profile
   (malleability defense).

5.3.  Validation rules (every receiver, every envelope)

   1.  Well-formed CBOR; tag 18; 4-element array; sizes within
       negotiated

   limits (§6.3) — else error 1000/1004.

   1.  protected.alg matches negotiated suite — else 1001.

   2.  Body[0] equals the negotiated version (in-session) or a supported

   version (out-of-session) — else 1001.

   1.  All keys listed in crit are understood — else 1002.

   2.  Timestamp within ±120 s of local clock (in-session) or within
       object

   class freshness rules (out-of-session) — else 1003.

   1.  Replay checks pass (§7) — else 1003.

   2.  Signature verifies against kid, or against the leaf key of a
       valid

   delegation chain terminating at kid's root (identity §6) — else
   2000/2003.

   1.  Sender authorization for msg-type in current state (per companion
       spec)

   — else 2005.  Failing envelopes MUST NOT cause state transitions;
   receivers SHOULD respond with ERROR (in-session) and MUST rate-limit
   error responses.

7.  Session Establishment and Negotiation

7.1.  HELLO / HELLO_ACK

   The connection initiator sends HELLO as its first envelope:

   Hello = {
     1 => [+ Version],        ; supported protocol versions, descending pref
     2 => [+ uint],           ; supported suites, descending pref
     3 => { * int => uint },  ; offered extensions: ext-key => max ext-version
     4 => uint,               ; max-message-size accepted (bytes; >= 65536)
     ? 5 => uint,             ; max concurrent tasks accepted
     ? 6 => bstr .size 32,    ; cookie (retry/DoS defense, §6.5)
     ? 7 => [* ZoneLabel]     ; zones the sender is willing to operate in
   }

   The responder selects the highest mutually supported version, the
   first mutually supported suite in the _initiator's_ preference order,
   and the intersection of extensions, replying HELLO_ACK:

   HelloAck = {
     1 => Version,            ; chosen
     2 => uint,               ; chosen suite
     3 => { * int => uint },  ; accepted extensions with chosen versions
     4 => uint,               ; responder's max-message-size
     ? 5 => uint,
     ? 8 => bstr              ; transcript-hash: H(HELLO bytes || this map
   }                          ;  fields 1..5 deterministically encoded)

   Note the field-shape asymmetry under identical field numbers: Hello
   fields 1/2 are _lists_ (offered sets) while HelloAck fields 1/2 are
   _singletons_ (the chosen values) — implementers regularly miss this;
   TV-001/TV-003 are the byte-level guard.






Larsen                   Expires 18 January 2027                [Page 8]

Internet-Draft              draft-map-core-01                  July 2026


   If no version or suite is mutual, the responder sends ERROR 1001 with
   the supported sets and closes.  Both peers MUST verify each
   envelope's signer matches the transport-authenticated identity (§7.3)
   — the HELLO exchange is therefore itself authenticated and MITM-
   resistant.

   The initiator's HELLO envelope carries a fresh SessionID (Body key
   6); the responder MUST echo the same SessionID in its HELLO_ACK
   envelope, and every subsequent in-session envelope carries it.  A
   SessionID mismatch is a state violation (1006) and the session MUST
   be closed.

7.2.  Downgrade resistance

   Both peers compute the negotiation transcript hash TH =
   H("MAPv1-transcript" || HELLO-envelope-bytes || HELLO_ACK-envelope-
   bytes) with the chosen suite's hash.  TH is mixed into the channel-
   binding token (§7.3).  An attacker who strips versions/suites from
   either HELLO alters TH and every subsequent signature check fails —
   closing threat TH14.

7.3.  Limits

   Default/floor limits: max-message-size 256 KiB (floor 64 KiB); larger
   payloads MUST use chunked CHUNK streams or content-addressed fetch.
   Peers MUST enforce their advertised limits and MUST NOT send beyond
   the peer's.  Receivers SHOULD enforce the size limit on the raw
   received frame before any decoding or signature work (cheapest check
   first; DoS posture §6.5).

7.4.  Version policy

   Version is (major, minor).  Minor revisions are strictly additive
   (new optional fields, new msg-types); implementations MUST accept
   unknown optional Body keys and unknown msg-types within a session by
   replying ERROR 3000 without closing.  Major revisions may break
   anything and never interoperate implicitly.  Deprecation process:
   draft-map-ops-01 §3.4.

7.5.  Denial-of-service posture at handshake

   Responders under load MAY reply to HELLO with ERROR 1005 carrying a
   cookie; the initiator retries HELLO including the cookie, proving
   reachability before the responder allocates session state (cf. DTLS/
   QUIC retry).  Signature verification precedes all allocation-heavy
   processing.

8.  Anti-Replay and Channel Binding

8.1.  Message-level

   Receivers maintain, per sender, a cache of MsgIDs seen within the
   last 10 minutes and MUST reject duplicates (1003) and out-of-window
   timestamps.  The cache bound is enforceable because of rate limits
   (§8.3).

8.2.  Session sequence numbers

   In-session envelopes carry seq, starting at 0 per direction and
   incrementing by 1.  Receivers MUST reject non-monotonic seq (1003).
   seq gives cheap ordering across multiplexed transports and makes
   transcript audits (tasks §8) unambiguous.

8.3.  Channel binding

   On session establishment each peer derives CB = HKDF(TH, transport-
   exporter, "map cb", 32) where transport-exporter is: the TLS 1.3
   exporter (EXPORTER-map-binding) for TLS/QUIC transports; the Noise
   handshake hash for Noise transports; for transports lacking an
   exporter, the concatenation of both peers' static public keys as
   authenticated by the transport.  CB is the COSE external_aad for
   every in-session envelope.  Consequences: an envelope recorded on one
   session cannot verify on another (anti-relay), and the signer is
   cryptographically bound to the transport-authenticated endpoint
   (TH4).  The transport identity MUST equal the envelope kid's key or a
   delegated key chained to it (identity §6); mismatch is error 2000 and
   immediate CLOSE.

8.4.  Out-of-session objects

   Descriptors, revocations, receipts, and other store-and-forward
   objects use empty external_aad, MUST carry ttl-ms, and are
   deduplicated by content address; freshness/supersession rules are per
   object class (e.g., descriptor seq, discovery §5.3).

9.  Flow Control and Rate Limiting

9.1.  Credit-based streaming

   Any message family that streams (task CHUNKs, evidence sets) is
   governed by receiver-granted credit.  FLOW_CREDIT content:







Larsen                   Expires 18 January 2027               [Page 10]

Internet-Draft              draft-map-core-01                  July 2026


   FlowCredit = {
     1 => TaskID / SessionID,   ; scope
     2 => uint,                 ; additional message credits
     3 => uint                  ; additional byte credits
   }

   Senders MUST NOT exceed outstanding credit in either unit; violations
   are 1005 and MAY be receipt-recorded.  Initial credits are granted in
   ASSIGN/ACCEPT (tasks §4).  Rationale: transport backpressure alone
   lets a slow or malicious reader pin provider resources (VRAM, queue
   slots) indefinitely — critique "no flow control".  Credit lets
   providers bound commitment and bill for reserved-but-unconsumed
   output.

9.2.  Keepalive

   PING/PONG carry an opaque 8-byte payload echoed verbatim; RECOMMENDED
   interval 30 s on idle sessions; 3 missed PONGs ⇒ session failure
   handling.

9.3.  Rate limits

   Implementations MUST enforce configurable per-peer ceilings on:
   envelopes/s, HELLOs/min from an address, STATUS_QUERYs/min, and DHT-
   record ingestion/s, with 1005 + exponential backoff hints (retry-
   after-ms in ERROR detail).

11.  Transport Bindings

   Common requirements: mutual authentication with keys verifiable
   against AgentIDs; confidentiality and integrity; ordered byte
   streams; multiplexing (or one connection per session).  Envelope
   framing on raw streams: 4-byte big-endian length prefix, then
   envelope bytes; length MUST respect negotiated max-message-size.

   *  *libp2p (RECOMMENDED)*: protocol ID /map/1.0.0; security Noise or

   TLS; muxer yamux; transports QUIC-v1 preferred, TCP, WebSocket,
   WebTransport.  PeerID MUST equal the AgentID key (identity §3.2).
   NAT traversal profile — AutoNAT v2, Circuit Relay v2, DCUtR hole
   punching — is REQUIRED for public-mesh providers (discovery §10).
   One MAP session runs per /map/1.0.0 substream, length-prefixed as
   above.

   _Channel binding for /map/1.0.0_ (§7.3 third clause — transports
   lacking an exporter): rust-libp2p does not portably expose a Noise
   handshake-hash / TLS-exporter equivalent on its stream API, so the
   exporter for this binding is initiator-AgentID || responder-AgentID
   (the two PeerIDs the connection authenticated, in stream-initiator-
   first order).  This binds the session to the authenticated identities
   of both endpoints.  Residual (acknowledged, weaker than a true
   exporter): it binds the identity _pair_, not the specific connection
   instance, so it does not by itself separate two concurrent
   connections between the same pair; the per-message msg-id replay
   cache and the monotonic in-session sequence numbers (§7.1) prevent
   cross-connection replay within the window regardless.  An
   implementation whose libp2p version exposes Noise handshake-hash
   material SHOULD use it instead and record that choice.

   *  *Raw QUIC*: ALPN map/1; TLS 1.3 with RawPublicKey or self-signed

   X.509 carrying the Ed25519 key; exporter per §7.3.

   *  *TCP+TLS 1.3*: ALPN map/1; same certificate rules.

   *  *WebSocket*: subprotocol map.v1; binary frames = framed envelopes;

   over TLS; where the WS layer terminates TLS at an intermediary, CB
   falls back to static-key binding and the session MUST be treated as
   Zone ≥2.

12.  Extension Framework

   Extension keys are integers from the MAP Extension Registry (ops §3).
   Rules: (a) unknown keys absent from crit MUST be ignored and, for
   stored/ forwarded objects, preserved byte-exactly (I3); (b) keys
   present in crit MUST be understood or the envelope rejected with
   1002; (c) extensions are version-negotiated in HELLO field 3 before
   use in-session; (d) extensions MUST NOT redefine core field
   semantics.  This mirrors the proven HTTP/TLS/COSE evolution model and
   is the mechanism by which bidding, KV-cache transfer, Git workspace
   sync, etc. attach without core changes.

13.  Session State Machine

                       send HELLO                    recv HELLO_ACK(ok)
           +------+  ------------->  +------------+  ---------------→ +-------------+
           | IDLE |                  | HELLO_SENT |                   |             |
           +------+  ------------->  +------------+                   |             |
               |       recv HELLO           | recv ERROR/timeout      | ESTABLISHED |
               |                            v                         |             |
               |                        +--------+   CLOSE sent/recv, |             |
               +--- (responder) ------> | CLOSED | <---- auth fail ---+-------------+
                    send HELLO_ACK,     +--------+        or 3×PING loss    |
                    enter ESTABLISHED        ^                              |
                                             +------------------------------

   ESTABLISHED admits all in-session message families per negotiated
   conformance classes.  CLOSE content carries an ErrorMsg-shaped
   reason.  Half-close is not modeled; either CLOSE tears down the
   session after flushing acknowledged state (task-level survival across
   sessions is handled by tasks §8 resumption, not by the session
   layer).

15.  Security Considerations

   Covered throughout: bytes-not-objects verification (§4, I1),
   deterministic encoding as malleability defense (§4.2), downgrade
   resistance (§6.2), handshake DoS (§6.5), replay and relay (§7),
   resource pinning (§8), information leakage via error verbosity (ERROR
   detail MUST NOT echo payload contents to unauthenticated peers).
   Residual: timestamp windows assume ±120 s clock sanity; deployments
   with worse clocks MUST widen windows and accept the enlarged replay
   cache, or deploy roughtime.

   *Channel-binding strength depends on the transport (§7.3, §10).* The
   anti-relay and endpoint-binding guarantees of §7.3 are only as strong
   as the transport-exporter fed into the CB derivation.  On transports
   that expose a true key-schedule exporter (TLS 1.3, raw QUIC — §10) CB
   binds the specific connection instance.  On transports lacking a
   portable exporter — notably the /map/1.0.0 libp2p binding as
   currently implemented, whose exporter is the authenticated initiator-
   AgentID || responder-AgentID pair (§10) — CB binds the identity
   _pair_ but not the specific connection, so it does not by itself
   separate two concurrent connections between the same pair; §7.1's
   per-message msg-id replay cache and monotonic in-session sequence
   numbers carry that separation within the window.  Deployments
   requiring instance-level binding MUST use an exporter-bearing
   transport (TLS/QUIC) or a libp2p stack that surfaces Noise handshake-
   hash material, and SHOULD treat the identity-pair fallback as Zone
   ≥2.  This is an implementation-maturity limitation of the reference
   libp2p binding, not a wire-format constraint: the CB derivation
   (§7.3) is unchanged across transports, so a stronger exporter drops
   in without a protocol change.
