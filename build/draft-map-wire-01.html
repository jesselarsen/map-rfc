MAP Wire Format and Registry Index

Abstract

This document is the wire-level reference for the MAP (Manolito Agent Protocol) family. It presents the protocol data unit layering — transport frame, signed COSE_Sign1 envelope over deterministic CBOR, protected and body headers, and message-type-selected content — as a single diagram with the field-level detail each layer's owning document specifies, so that an implementer can see the whole encoding in one place. It then consolidates every code point the family assigns: message types, error codes, body and protected-header keys, cryptographic suites, capability-ontology terms, delegation caveats, chunk kinds, settlement methods, pricing models, dispute claim codes, and the remaining registries, each with its registration policy and a pointer to the document that owns it.¶

This document is an index, not a normative source. Where it disagrees with an owning document, the owning document governs. It defines no protocol behavior of its own and requests no IANA action of its own.¶

2. Purpose and how to read this document

This document is the consolidated, non-normative index of the MAP wire format and of every assigned registry in the family. It exists so a reader can see the whole on-the-wire picture and the complete code-point space in one place, without opening all eight normative drafts.¶

It is an index, not a normative source. The normative definitions — CDDL, validation rules, MUST/SHOULD requirements, and the exact bytes — remain in the owning documents listed below. Where this index and an owning document disagree, the owning document wins (engineering policy: one named source of truth per fact, ops §2 rule 1).¶

3. The MAP Protocol Data Unit (PDU) layering

Every MAP message is a signed CBOR/COSE envelope. The layering, top to bottom:¶

AgentID / key material                      (identity §3)
        │
        ▼
Envelope = COSE_Sign1                       (core §4)
   [ protected(ProtHdr), payload(Body), signature ]
        │
        ▼
Body = {                                     (core §4.1)
   version, msg-type, msg-id, timestamp,
   [recipient], [ttl-ms], [session-id], [seq],
   [crit], [ext], content }
        │
        ▼
content := selected by msg-type             (core §5 registry → owning doc)
   HELLO / HELLO_ACK / PING / PONG / CLOSE /
   ERROR / FLOW_CREDIT                        (core §6, §8, §9)
   DESCRIPTOR / STATUS_QUERY / STATUS_REPORT /
   CAP_QUERY / CAP_RESPONSE                   (discovery §2, §3, §7)
   OFFER / QUOTE / ASSIGN / ACCEPT / REJECT /
   CHUNK / TOOL_CALL / TOOL_GRANT / TOOL_RESULT /
   CHECKPOINT / CHECKPOINT_ACK / CANCEL / COMPLETE /
   RESUME / RESERVE / LEASE / LEASE_RELEASE   (tasks §2–§6, §8, §11)
   RECEIPT / RECEIPT_ACK / EVIDENCE_QUERY /
   EVIDENCE_SET / CHALLENGE / CHALLENGE_RESPONSE  (trust §2, §4, §8)
   PAY_QUOTE / PAY_AGREE / PAY_INVOICE /
   PAY_PROOF / PAY_RECEIPT / PAY_DISPUTE /
   PAY_DISPUTE_EVIDENCE                       (pay §2–§6)
        │
        ▼
Task transcript commitment                   (tasks §8.1)
   Merkle root over output/tool CHUNKs (kinds 0, 1, 4)
¶

Two transmission contexts (core §7):¶

  • In-session: the envelope's COSE external_aad is the channel-binding¶

token CB (core §7.3); recipient, session-id, and seq are REQUIRED.¶

  • Out-of-session (descriptors, receipts, revocations, provider records):¶

external_aad is empty; ttl-ms is REQUIRED; freshness/supersession rules are per object class (core §7.4).¶

Four design invariants bind every layer (core §1):¶

  • I1 — signatures cover the exact transmitted bytes; verifiers MUST NOT¶

re-serialize before verifying.¶

  • I2 — every envelope is independently verifiable from the sender's key¶

material alone.¶

  • I3 — unknown non-critical fields are ignored and preserved verbatim¶

when stored or forwarded.¶

  • I4 — all normative structures are CDDL (RFC 8610) over the deterministic¶

CBOR profile (core §4.2; RFC 8949 §4.2.1).¶

Table 8

6. Conformance classes

MAP-Core (REQUIRED: identity + core); MAP-Discovery; MAP-Tasks; MAP-Trust; MAP-Pay; MAP-Fed (arch §10). A conforming provider/requester implements Core + Discovery + Tasks; Trust and Pay are RECOMMENDED on public meshes.¶

7. Security Considerations

This document is a wire-format layering summary and a consolidated registry index; it introduces no mechanism beyond those in the protocol documents, whose security considerations apply unchanged. In particular, all code-point and key registrations indexed here are consumed under the deterministic-CBOR and signed-envelope rules of draft-map-core-01 §4, whose Security Considerations govern malleability, downgrade, and replay.¶

8. IANA Considerations

This document defines no new registry of its own. It provides a consolidated index (§3) of the registries defined by the MAP protocol documents; each registry's contents, assignment policy, and change control are normative in its defining document, and the registration policies are summarized in §4. No IANA action is requested by this document beyond those already requested by the protocol documents it indexes.¶
