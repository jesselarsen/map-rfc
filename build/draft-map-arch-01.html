The Manolito Agent Protocol (MAP): Architecture, Requirements, and Threat Model

Abstract

The Manolito Agent Protocol (MAP) is a family of specifications for a decentralized, permissionless network of autonomous AI agents. MAP evolves the capability-oriented spirit of the historical Manolito (MP2P) file-sharing network into a modern agent fabric: participants advertise what they can do — models, tools, memory domains, compute — and requesters route work by semantic capability, verifiable evidence of past behavior, price, and locally measured performance. This document defines the architecture, design goals and non-goals, the system and trust models, the threat model, the privacy model (including data-sensitivity zones), scalability targets, and the map of companion documents. It contains no wire formats; those are defined in draft-map-core-01 and its siblings.¶

1. Introduction and Heritage

Manolito/MP2P (c. 2001) demonstrated that a flat, serverless, UDP-centric network of consumer nodes could sustain search and exchange at scale with minimal per-node state. MAP retains three MP2P instincts — decentralization without supernodes, lightweight signed messages, tolerance of extreme churn — and discards its obsolete mechanics (cleartext UDP, file-hash indexing, no identity layer). The essential inversion is this: MP2P asked "who has this file?"; MAP asks "who can do this task?". The network is a capability graph.¶

MAP is a protocol, not a product. "Hermes" and similar orchestrators are implementations that speak MAP; nothing in these documents privileges any implementation.¶

3. Terminology

  • Agent: a protocol participant identified by an AgentID. May act as¶

Requester, Provider, Relay, Gateway, or several at once.¶

  • AgentID: a self-certifying identifier derived from an Ed25519 public¶

key (draft-map-identity-01).¶

  • Requester / Provider: the party commissioning a task / the party¶

executing it. Roles are per-task, not per-node.¶

  • Orchestrator: application logic on a requester that decomposes,¶

routes, and merges tasks. Out of protocol scope except where it emits MAP messages.¶

  • Descriptor: a signed, content-addressed advertisement of an agent's¶

stable properties (draft-map-discovery-01).¶

  • Capability: a registered hierarchical URI naming a service class,¶

e.g. map:cap:inference/text-generation (draft-map-discovery-01 §4).¶

  • Envelope: the signed CBOR/COSE container for every MAP message¶

(draft-map-core-01).¶

  • Receipt: dual-signed evidence of a completed interaction¶

(draft-map-trust-01).¶

  • Zone: a data-sensitivity class constraining where payloads may flow¶

(§8).¶

  • Mesh: a connected deployment of MAP agents sharing bootstrap and¶

policy; meshes MAY federate (draft-map-ops-01).¶

4. Design Goals

G1. Decentralized and permissionless. No central authority, registry server, or global PKI is required to join, advertise, discover, or transact. (Governed namespaces — the capability ontology, code-point registries — are documents and processes, not runtime services.)¶

G2. Self-certifying identity. Every artifact that matters — descriptor, task assignment, checkpoint, receipt, payment message — is signed and verifiable offline against the sender's AgentID.¶

G3. Capability-first semantics. Discovery, negotiation, and routing operate on capabilities and constraints, never on addresses as such.¶

G4. Local trust. No global reputation exists. Each agent computes its own trust from evidence it can verify. Identity does not imply reputation; anonymous participation is permitted and simply starts with none.¶

G5. Transport agnosticism. MAP runs over any ordered, bidirectional, mutually authenticated, encrypted, multiplexed byte stream. libp2p over QUIC is the RECOMMENDED substrate; TCP+TLS/Noise and WebSocket bindings are normative; future transports slot in without protocol change.¶

G6. Secure and private by default. All traffic encrypted; all control messages signed; replay-protected; metadata minimized; data-sensitivity zones enforced by protocol rule, not convention.¶

G7. Cryptographic agility. Algorithms are named by negotiated suite identifiers; the protocol survives replacement of any primitive, including migration to post-quantum signatures/KEMs.¶

G8. Extensible without forking. Unknown non-critical extensions are ignored and preserved; critical extensions are negotiated; all code points live in registries with defined policies.¶

G9. Economically open. Payment negotiation is standardized; payment settlement is pluggable (Lightning, card processors, stablecoins, ACH, Interledger, private ledgers). The protocol never mandates a currency, chain, or processor.¶

G10. Operable at scale and at the edge. Target: 10^9 identities, 10^7 concurrently reachable providers per mesh, individual nodes as small as a single-board computer. Mechanisms whose cost grows super-logarithmically with network size are excluded from the mandatory core (§9).¶

G11. Honest about churn and failure. Mobile, NATed, intermittently connected agents are first-class; every long-lived operation defines timeout, resumption, and compensation behavior.¶

4.1. Non-Goals

  • Model training or fine-tuning coordination.¶
  • General-purpose file sharing (content transfer exists only in service of¶

tasks).¶

  • A native token, blockchain, or consensus layer.¶
  • Global, objective reputation scores.¶
  • Guaranteeing the semantic quality of AI outputs — MAP makes behavior¶

attributable and evidence-bearing, not correct.¶

  • Backward wire compatibility with legacy Manolito clients (a conceptual¶

migration guide is provided in draft-map-ops-01 §7).¶

¶

Roles: Relays forward encrypted traffic for unreachable peers (they see ciphertext and coarse metadata only). Gateways re-advertise external services (e.g., a hosted-API bridge) into a mesh, with mandatory provenance labeling. Bootstrap peers are ordinary agents listed out-of-band; they hold no authority.¶

6. Trust Model (Assumptions)

T1. No participant is trusted by default; the network is assumed to contain actively malicious, colluding, well-resourced adversaries. T2. Every protocol-relevant claim MUST be independently verifiable or explicitly marked as an unverifiable assertion (e.g., a rating). T3. Identity is cheap unless a mesh applies admission costs; therefore no mechanism may assume identities are scarce (Sybil-aware design). T4. Trust decisions are local. Two honest agents may legitimately disagree about a third. T5. Reputation derives only from evidence signed by counterparties, weighted by the evaluator's trust in those counterparties. T6. Transports provide confidentiality and integrity between endpoints once established; endpoint identity binding is MAP's responsibility (channel binding, draft-map-core-01 §7.3). T7. The cryptographic primitives of the negotiated suite are sound; clocks are loosely synchronized (±120 s); no global time authority exists. T8. Availability of any single peer, relay, or bootstrap node is never assumed.¶

7. Threat Model

Adversary capabilities considered: create unlimited identities; observe and inject on any public network path; participate as provider, requester, relay, and gateway simultaneously; collude; replay recorded traffic; run modified implementations; control substantial compute. Out of scope: global passive adversaries deanonymizing via traffic timing across the entire Internet (mitigated only partially, §8.3); compromise of a victim's own endpoint.¶

8. Privacy Model

8.1. Zones (normative)

Every payload-bearing object carries a zone label; every peer relationship has a zone level assigned by local policy.¶

  • Zone 0 — Local: this device only. Never leaves the host.¶
  • Zone 1 — Trusted: explicitly allowlisted peers (own fleet, partners).¶

Raw proprietary data (source code, documents, embeddings of them) MAY flow here.¶

  • Zone 2 — Community: authenticated but untrusted mesh peers. Only¶

abstracted or non-sensitive payloads.¶

  • Zone 3 — Open: anonymous/ephemeral counterparties and public¶

gateways.¶

Rule Z1: An agent MUST NOT transmit an object to a peer whose zone level exceeds the object's zone label. Rule Z2: A provider MUST NOT forward received task content to a higher-numbered zone than it was received under (no laundering); delegation carries the label. Rule Z3: Zone violations are protocol errors (code 2004) and receipt-recordable events.¶

8.2. Data minimization requirements

  • Descriptors: hardware in coarse buckets (e.g., VRAM class ∈ {≤8, 16, 24,¶

32, 48, 64, 96, 128, >128} GB); exact figures OPTIONAL and zone-gated; no serials, hostnames, or OS fingerprints.¶

  • No latency, load, or trust figures in long-lived records (they are either¶

meaningless or volatile — see critique C3/C6).¶

  • Receipts disclose to chosen audiences on request; global broadcast of¶

receipts is NOT RECOMMENDED.¶

  • Intermediate task data MUST be deleted after settlement unless retention¶

is negotiated.¶

8.3. Residual risks (honest statement)

DHT queries reveal interest in a capability to the queried nodes; status queries reveal requester–candidate pairs; relays learn traffic timing. Mitigations offered (shard sampling, relayed queries, decoy traffic, ephemeral identities per draft-map-identity-01 §8) reduce but do not eliminate these. Deployments with strong anonymity needs SHOULD run MAP over an anonymity network and use Zone-3 ephemeral identities.¶

9. Scalability Analysis and Targets

Costs in the mandatory core are bounded as follows (N = mesh size, P = providers of a capability):¶

  • Discovery lookup: O(log N) DHT hops; hot capabilities sharded so any¶

single key holds O(P / S) records for S shards (discovery §6).¶

  • Stable-record maintenance: one descriptor republish per agent per hour —¶

~278 puts/s per million agents mesh-wide, absorbed by the DHT.¶

  • Volatile state: pulled on demand from a shortlist (typically ≤ 10 status¶

queries per routing decision); optional presence gossip is topic-scoped and rate-limited to ≥30 s intervals.¶

  • Per-connection state: O(active sessions), independent of N.¶
  • Trust: evidence storage is local and prunable; no global convergence¶

required (EigenTrust-style global iteration is explicitly OPTIONAL and off the critical path).¶

Anything violating these bounds (global broadcast, per-second global republish, global consensus) is excluded from mandatory conformance — this is the structural fix for critique C3.¶

10. Conformance Classes

  • MAP-Core (REQUIRED): identity + core envelope/sessions/errors.¶
  • MAP-Discovery: descriptors, ontology, DHT/status planes.¶
  • MAP-Tasks: task lifecycle, streaming, tools, checkpoints.¶
  • MAP-Trust: receipts and evidence exchange.¶
  • MAP-Pay: payment negotiation (≥1 settlement method).¶
  • MAP-Fed: federation gateways.¶

A conforming provider implements Core+Discovery+Tasks; a conforming requester Core+Discovery+Tasks; Trust and Pay are RECOMMENDED for public meshes. Test-suite structure: draft-map-ops-01 §6.¶
