**Recommendation per document:**
- **index, intro, arch, wire** — keep `info`. No change needed; RFC 7841 §3.3 permits this on the ISE track. Note: `index` and `intro` have near-duplicate abstracts (both open with "The Manolito Agent Protocol (MAP) is a ... decentralized, permissionless ... network of autonomous AI agents" — `draft-map-index-01.md`, `draft-map-intro-01.md`, `draft-map-arch-01.md` all restate this). - **ops (`bcp`)** — **must** change; BCP is not just off the ISE's menu, it's an IETF-community-process category by definition (RFC 2026 §5) — there is no "recategorize as Informational for the ISE" ambiguity here, unlike the `std` docs. Recategorize Informational.

## 2. Eleven drafts at once — not realistic

The ISE is a small volunteer operation; an unaffiliated single author submitting an 11-document, tightly cross-referencing family simultaneously is exactly the kind of intake that gets returned for staging before review starts. Recommended sequence:

1. **index + intro** — merge these two (overlapping abstracts noted above; index's actual unique content is the reading-order table and submission-status record, which could be a section of a combined "Introduction and Family Index" doc). Submit first — no registries, no wire format, establishes context.
2. **arch** — distinct content (threat model, zones, non-goals), submit alongside or right after.
3. **wire** — hold until the six owning documents' registries are stable; wire says explicitly "the owning document wins" on conflict (`draft-map-wire-01.md:39`), so submitting it first risks it going stale mid-review.
4. **core, identity, discovery, tasks, trust, pay** — these can't be meaningfully split further (heavy cross-reference), but expect the ISE to review `core` first as foundational and gate the rest on it.
5. **ops** — last; it references the interop matrix and registries owned by the other six, and its governance content only matters once those have a reviewer's attention.

Don't upload all 11 in one Datatracker session even if nothing above blocked it — a single reasonable-length cover note (see (c)) explaining the staged plan will do more for this submission than any formatting fix.

## 3. Boilerplate

The hand-written "Status of This Memo" paragraph (e.g. `draft-map-core-01.md:12-19`) is **stripped entirely** before rendering — confirmed in `build/md2rfc.py:222-228`, which drops all preamble prose before the first heading on the stated rationale that "xml2rfc regenerates the correct boilerplate... keeping the prose in the body would duplicate it." So it cannot literally conflict with the rendered output, because the two never coexist in the same artifact — but it's misleading to anyone reading the `.md` source believing that's what ships.

Two real issues underneath it:

- **The task brief's specific claim is false, and worth flagging as an example of why to verify rather than trust `SUBMISSION.md`/comments.** `build/render.py:24-36` defines a `DRAFTS` list with a per-entry `ipr` field, and every entry is `"none"`. But that field is **dead code** — `grep -n "ipr" build/render.py` shows it's unpacked in the loop (`for name, abbrev, ipr in DRAFTS:`) and never referenced again. The actual XML is built by `md2rfc.py:254`, which reads `ipr` straight from each draft's own frontmatter (`fm.get("ipr", "trust200902")`). I confirmed the rendered output: `build/draft-map-core-01.xml:2` and all three other spot-checked files emit `ipr="trust200902"`, not `"none"`. **Not a real defect in the rendered XML.** It *is* worth deleting or wiring up that unused tuple field in `render.py`, since it's exactly the kind of vestigial artifact that produces false alarms like the one in this review's own brief.
- **A real, silent defect that the brief didn't ask about but should have.** `md2rfc.py:252` only emits `submissionType="independent"` when `category in ("info", "exp", "historic")`. All 11 drafts declare `submissiontype: independent` in frontmatter, but the 7 `std`/`bcp` drafts lose that attribute on render — confirmed: `build/draft-map-core-01.xml:2` and `build/draft-map-ops-01.xml:2` carry no `submissionType` attribute at all, while `build/draft-map-index-01.xml:2` and `build/draft-map-wire-01.xml:2` do. This is the actual, wire-level manifestation of the item-1 conflict, and it's invisible in the rendered text: `build/md2rfc.err` (where `render.py` would log stderr) is empty because `render.py:62-69` only captures stderr into the `failures` list **when the subprocess returns non-zero** — a successful-but-warning-emitting xml2rfc run discards its own warnings. Fix: log stderr unconditionally.
- **A coincidental, confusing visual.** The rendered header for every draft shows `Internet-Draft ... Independent` (e.g. `build/draft-map-core-01.txt:6`, `build/draft-map-index-01.txt:6`) — identical for both. This is *not* a stream indicator; it's `author_xml()`'s default organization fallback (`md2rfc.py:61`: `org = fm.get("organization", "Independent")`), and no draft sets `organization:` in frontmatter. A reviewer skimming the rendered header could easily mistake this for stream confirmation, when for 7 of 11 drafts the actual stream attribute is silently absent. Recommend setting an explicit `organization` value (or deliberately omitting the field so no line renders) purely to stop this false cue.
- **Minor conceptual confusion, source-only:** `draft-map-core-01.md:21` — "The source working tree is distributed under Apache-2.0 (see repository LICENSE); contributors SHOULD disclose relevant IPR per BCP 79." BCP 78/79 govern IPR in the *document text* contributed to the IETF Trust, not the reference-implementation code's license; conflating the two in the boilerplate paragraph is wrong even though it's stripped at render — clean it before it gets copied into a cover note.

## 4. References

Confirmed for all 11 drafts: a body-level `## References (selected)` (or numbered variant, e.g. `draft-map-wire-01.md:313`: `## 8. References (selected)`) instead of RFC 7991 back-matter. `md2rfc.py:279` hardcodes `<back></back>` — empty, always — so every "References" heading is processed as an ordinary numbered body `<section>`. Visible consequence in the rendered TOC: `build/draft-map-core-01.txt:104` — `17.  References (selected)` — numbered exactly like any other section, which real RFC back-matter never is.

**Exactly what must change:** per-entry `<reference anchor="RFCxxxx">` elements (or `<xi:include>`s against the standard bibxml pool), inside `<back><references><name>Normative References</name>...</references><references><name>Informative References</name>...</references></back>`. `md2rfc.py` needs a dedicated parser for this section instead of routing it through `render_sections()`.

**A citation gap the "(selected)" framing was hiding:** I swept every draft's body `[RFCxxxx]` citations against its own reference list. Ten of eleven match exactly. `draft-map-core-01.md` does not:

- Used in body (§2 crypto-suite table etc.): `[RFC2119] [RFC5869] [RFC7748] [RFC8032] [RFC8174] [RFC8439] [RFC8610] [RFC9052]`
- Listed at `draft-map-core-01.md:521`: `[RFC2119] [RFC8174] BCP 14 requirement levels.` — only two.

**Missing, normatively cited, and absent from the reference list entirely: RFC5869 (HKDF), RFC7748 (X25519/X448), RFC8032 (EdDSA), RFC8439 (ChaCha20-Poly1305), RFC8610 (CDDL), RFC9052 (COSE).** This is core's crypto-suite specification — these are about as normative as a citation gets. **BLOCKING.**

The heading word "(selected)" is itself a problem to carry forward: a Normative References list has to be exhaustive for anything a MUST/SHOULD depends on, not "selected."

## 5. IANA

Heading check (`grep -n "^#.*IANA"` across all 11):

| Uses **"IANA Considerations"** | Uses **"IANA-Style Considerations"** |
|---|---|
| arch, index, intro, ops, wire | core, discovery, identity, pay, tasks, trust |

Notice the split is exactly the `info`/`bcp` docs vs. the `std` docs — i.e., precisely the ones that actually carry registrations use the nonstandard heading.

**Is "IANA-Style" acceptable?** No. idnits and IANA's own draft-intake tooling key off the literal heading "IANA Considerations" to locate registration requests. A document that defines real code points under a heading that reads as a hedge risks the request simply not being picked up — not a style nit, a functional risk for documents that do contain actionable registrations.

**RFC 8126 adequacy of the 20 registries in wire §3:** partial, and this is the biggest friction point in the whole submission, bigger than the stream/category question:

- **Positive:** `map-spec/draft-map-wire-01.md:103-233` (§3.1–3.16) states a registration policy per registry (Standards Action / Specification Required / Expert Review / Private Use), and `map-spec/draft-map-ops-01.md:82-93` (§3) tabulates the same policies with rationale.
- **Gap — no named change controller.** RFC 8126 §5.5 wants an explicit change controller per registry. `ops §3.5` (`map-spec/draft-map-ops-01.md:117-135`) gestures at "the document editor(s) named on the front matter" pre-publication and IANA post-publication, but that phrase appears only in `ops`, never inside any of the six actual IANA-considerations sections where IANA looks for it.
- **Gap — no named designated experts.** `map-spec/draft-map-ops-01.md:95-97`: "Two or more per registry, appointed by the project's steering process" — no names. IANA routinely bounces Expert-Review/Specification-Required registries that don't have an actual appointed expert at submission time.
- **Gap — the sections aren't requests.** Sampled `draft-map-core-01.md:510-517` (§15): "This document establishes (initial contents above; policies in ops §3): MAP Cryptographic Suites; MAP Message Types; ... The assigned values ... are in `draft-map-wire-01.md` §3.1 ... §3.6." This is a pointer/summary, not the "IANA is requested to create a registry named X, located at Y, with initial contents Z, using policy W" language IANA needs to act on. All six std-doc sections read this way.
- **The one document with all 20 registries tabulated explicitly disclaims making the request.** `draft-map-wire-01.md:304-310` (§7): *"This document defines no new registry of its own... No IANA action is requested by this document beyond those already requested by the protocol documents it indexes."* Combined with the previous point, there is currently **no single section anywhere in the family** that both lists a registry's full initial contents *and* actually requests it.

**How much friction:** substantial — I'd rate this the single largest procedural risk in the family, ahead of the stream/category question (which is at least a well-trodden binary decision the ISE handles routinely).
