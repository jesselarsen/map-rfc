## 3. Test-vector self-reference audit (the important one)

`map-spec/test-vectors/gen_vectors.py` is the **sole source** of every TV/NV byte string. Both conformance suites reproduce *this script's own output*, not each other's and not any external oracle. Precisely:

- **What's genuinely independent:** Ed25519 signing/verification runs through `pynacl` (libsodium binding) — real third-party crypto, not author code. Deterministic CBOR encoding runs through `cbor2`'s `canonical=True` — a real third-party encoder. Multibase base58btc runs through the `base58` package. **Crucially**, `map-go/identity` verifies these same pynacl-produced signatures using **Go's stdlib `crypto/ed25519`** (`TestVerifyStrictAcceptsValid` et al.) — a genuinely independent, cross-language re-verification of the raw Ed25519 math (RFC 8032). That part of "byte-exact parity" is real evidence, not circular.
- **What's self-referential:** every *protocol-layout* choice — field numbers, which fields are lists vs. singletons, the Merkle-leaf preimage format, the DHT key preimage string, which fields exist in which message — comes from this one script, written by the one author of both implementations and both drafts. The TV-001/TV-002 "regression guard" bytes are literal hex strings hardcoded in `gen_vectors.py` and asserted equal *within the same script* — they were produced by an earlier run of this same code, not derived independently.
- **Consequence:** a bug shared by the spec text, `gen_vectors.py`, and both implementations (e.g., a wrong field number, a wrong Merkle preimage) would be invisible to the entire test-vector apparatus, because all three trace to the same design decisions by the same person. This is close to structurally unavoidable for a brand-new protocol (there is no independent MAP implementation to check against), but it means "byte-exact test-vector parity" should be read narrowly: it proves the two implementations converged on the *same reading* of the spec, not that the reading is *correct* against anything external.
- **Nothing in the repo cross-checks against a published RFC 8032 Ed25519 KAT, an RFC 8949 §4.2 published CBOR example, a third-party COSE_Sign1 test vector, or an external multihash/DHT tool.** That would be the cheapest way to close this gap for the crypto/encoding primitives (the protocol-layout part can't be externally anchored — there's nothing to anchor it to).

**#5 is the finding that matters.** `map-go/dht/dht_test.go::TestDescriptorPublishFetch` hard-asserts the local publish/fetch round-trip (codec + local store — genuinely tested), but the actual cross-node Kademlia lookup is wrapped in `if err != nil { t.Logf(...) } else { if !found { t.Logf(...) } }` — **every branch is `t.Logf`, none is `t.Fatalf`/`t.Errorf`.** I made `FindProviders` a no-op that always returns zero providers; the full suite still reported `ok` for every package. ## 5. Independence rule (ops §6.1 two-impl bar)

`go list -deps` confirms `AGENTS.md`'s claim exactly: `cbor`, `envelope`, `identity`, `session`, `hello`, `receipt`, `discovery`, `conformance`, plus `pay` and `tasks`, are **entirely libp2p/multiformats/mr-tron-free**; libp2p-family deps appear only in `net`, `dht`, `cmd/*`. On the *mechanical* independence question, the claim holds.

On the *substantive* independence question the brief actually asks ("independent enough... given one author wrote both"): it doesn't, and can't, by construction. One person authored the drafts, `gen_vectors.py`, and both codebases. The Go implementation not consulting Rust *source* is a real and useful discipline (it forces two honest readings of the same spec text, which is how `AGENTS.md`'s own "wrongsid" note — Go implemented the SessionID check first, Rust was missing it and got patched — happened), but it is not the same as two implementations from two independent teams with two independent readings of intent. Report this as: mechanical bar met, substantive two-vendor bar not met and not really achievable solo — that's a disclosure item for the ISE cover note, not a defect.

## 6. Ambiguity report (`map-go/README.md` §"Ambiguity report") vs. current -01 text

All five are **already resolved in the -01 drafts** — the report is stale, not wrong-but-still-open:

1. **Sharded-key text format** — `draft-map-discovery-01.md` §6 (line 233): *"`s` is rendered as its unpadded base-10 ASCII decimal ('0'..'255' — e.g. shard 141 contributes the three bytes `31 34 31`), not as a raw byte or hex; the derived-constants test vector K′ fixes this form."* Resolved.
2. **Delegated-envelope kid** — `draft-map-identity-01.md` §4 (line 117): *"the envelope `kid` MUST equal the chain LEAF's subject... and the verifier resolves the chain root's issuer as the accountable identity."* This directly contradicts the README's claim that the draft says "chain root MUST equal envelope kid" — the draft has already been patched to say LEAF, matching TV-012 and the Go code. Resolved.
3. **Max-depth counting** — same §4 (line 120): *"a chain is invalid (2003) when any certificate has more certificates between itself and the leaf than its declared max-depth — a cert with max-depth 0 must itself be the leaf cert."* Matches the Go implementation's chosen reading exactly. Resolved.
4. **HELLO vs HELLO_ACK field shapes** — `draft-map-core-01.md` §6.1 (line 232): *"Note the field-shape asymmetry under identical field numbers: Hello fields 1/2 are lists... while HelloAck fields 1/2 are singletons... implementers regularly miss this; TV-001/TV-003 are the byte-level guard."* Already explicit. Resolved.
5. **Policy-reject NVs (NV-006/008)** — `draft-map-pay-01.md` §3.1 (line 145) and `draft-map-tasks-01.md` §6 (line 260) both explicitly say the receiver "MUST treat [it] as a rejection" / "reject or re-quote" with **no wire code**, matching `gen_vectors.py`'s own comment that these are policy rejections, not core §9 errors. Already explicit, and correctly *not* inventing a code. Resolved.
