## 2. Registry integrity findings

Owning drafts checked in full against `draft-map-wire-01.md` §3, cross-checked against `map-test-vectors.md` and both implementations' source constants.

- **§3.1–§3.20, value-for-value: consistent**, except the two items below. Every hex message type, error code, key number, chunk kind, and other coded value in the six owning drafts (core/identity/discovery/tasks/trust/pay) matches wire-01 §3 exactly, and matches every test vector's decoded bytes (TV-001 through TV-020 + TV-010b, NV-001 through NV-012, all independently hand-verified against the wire values). `map-rs/crates/map-core/src/msg_type.rs`'s full 33-constant table matches wire-01 §3.2 byte-for-byte (directly inspected, not just agent-reported). Error codes 1000-6010 in `map-rs/crates/map-core/src/errors.rs` match wire-01 §3.5 exactly, including the newer 6005-6010 additions.
- **Missing registry entries (wire-01 is not actually the complete "single source of truth" it claims to be):** `PayReceipt.kind` (0 settled, 1 held, 2 released, 3 refunded — `pay-01` §5.2.1, fail-closed enforced via error 6010) and `PayInvoice.phase` (1 hold, 2 release — same section) are both real, assigned, fail-closed-enforced code points, but **neither appears anywhere in `wire-01` §3** (no subsection covers them). Given wire-01 §1 states it's "the consolidated, non-normative index... of every assigned registry in the family," this is a genuine omission. *Severity: MAJOR.* Fix: add a wire-01 §3.21 for these two fields.
- **Internal contradiction, not a wire-01 mismatch:** the identity-01 chain-length 8-vs-5 contradiction (table row #9) doesn't surface at the wire-01 rollup level (wire-01 states no chain-length cap at all), but is live in the normative text implementers actually read.
- **Internal contradiction, not a wire-01 mismatch:** the discovery-01 CapEntry `int`/`uint` divergence (table row #23) — wire-01 §3.11 doesn't state a key type either, so this is invisible at the rollup level too.
- **Cosmetic, not a value mismatch:** core-01 §2 calls suite 3 "hybrid Ed25519+ML-DSA-44"; wire-01 §3.1 drops "hybrid" and says "(reserved, post-quantum)". Same suite ID, same primitives. NIT.
- **Implementation-completeness gap (see table row #25):** registered code points with no working codec in one or both implementations. This doesn't create a *value* mismatch (every value that *is* implemented is correct), but it means the "two independent interoperating implementations" claim doesn't currently cover: tool invocation, checkpoint/resume, canary challenges, key rotation/revocation (map-rs, partial; map-go, entirely absent) — and additionally, in map-go only: STATUS_QUERY/STATUS_REPORT, CAP_QUERY/CAP_RESPONSE, RECEIPT/RECEIPT_ACK/EVIDENCE_QUERY/EVIDENCE_SET.
- **Not examined:** `map-net`, `map-session`, `map-cli`, and `adapters/*` were spot-checked by grep for the registry hex ranges (came back clean) but not read line-by-line for definitional completeness; `formal/` and `build/` were not checked for registry-consistent numbers (out of scope for code-point integrity); `draft-map-arch-01/intro-01/index-01/ops-01` were not checked against wire-01 §3 since wire-01 states it's copied from the six owning docs specifically (ops-01 is the *policy* document for the registries, not a value source).

## 3. CDDL findings

30 CDDL blocks total, confirmed present across only 6 of 11 drafts (core, discovery, identity, trust, tasks, pay); `arch-01`, `intro-01`, `index-01`, `wire-01`, and `test-vectors/map-test-vectors.md` contain zero CDDL blocks (diagrams/prose/CBOR-diagnostic-notation only). No offline CDDL validator was available (no `cddl` npm package, no Python cddl library reachable without a fresh network install, which was declined); all "parses"/"does not parse" verdicts below are manual RFC 8610 grammar review, not tool-verified.

- **BLOCKING — invalid CDDL, does not parse.** `draft-map-tasks-01.md` §12, `CtxQuery.3`: `[+ float16/float32 as bstr]` — `as` is not a CDDL operator. Same block, `CtxQuery.5`: `float-as-decimal` is not a CDDL primitive and is never defined as a rule anywhere in the family.
- **BLOCKING — invalid CDDL, does not parse.** `draft-map-tasks-01.md` §8.2, `Checkpoint.5`: `{ usage as in Complete.4 }` — this is English prose written inside CDDL braces, not a type expression. A decoder generated from this grammar cannot type this field at all.
- **MAJOR — dangling type `Usage`.** Referenced by name in `pay-01` §4 (`UsageWatermark.3 => Usage`) and informally in tasks-01/trust-01 prose, but **no document anywhere defines `Usage = {...}` as a CDDL rule**. Every consumer independently inlines the same anonymous 4-field shape. `map-rs/crates/map-tasks/src/msg.rs` *does* define a concrete `pub struct Usage` — the implementation invented the canonical shape the spec never wrote down. `ERRATA.md` even calls it "the existing Usage map shape" as if it were already normatively pinned. Fix: add `Usage = { 1 => uint, 2 => uint, 3 => uint, 4 => uint }` to core-01's common types (§3) and reference it everywhere (also fixes the Checkpoint.5 BLOCKING item above).
- **MAJOR — dangling type `ContextRef`.** `tasks-01` §2.1, `InputSpec.3 => [+ ContextRef]` — never defined anywhere. Confirmed as a known, acknowledged gap: `map-rs/crates/map-tasks/src/msg.rs` has a comment admitting "the draft leaves ContextRef's shape open," and it's carried as an opaque `Value`. `ERRATA.md` references it without ever pinning a shape.
- **MAJOR — `Amount`'s CBOR tag silently dropped.** `pay-01` §1 canonical: `Amount = #6.4([int, int])` (tagged). `discovery-01` §2 `PricingHint.2`/`.3`: bare untagged `[int, int]`, with a comment saying "tag-4" that the actual CDDL type doesn't enforce. A decoder built strictly from discovery's grammar won't expect/require tag 4 here.
- **MAJOR — inconsistent `bstr` sizing for the same logical identifier, within `pay-01` itself.** quote-id: `.size 16` in `PayQuote.1`/`PayAgree.1`, but unconstrained `bstr` in `PayInvoice.2`. invoice-id: `.size 16` in `PayInvoice.1`, but unconstrained in `PayProof.1`/`PayReceipt.1`. Both reference implementations quietly assume 16 bytes everywhere (code is stricter and more consistent than the spec text). Fix: introduce named `QuoteID`/`InvoiceID` aliases in core §3 and use them everywhere instead of inlining `bstr` with inconsistent constraints.
- **MAJOR — HELLO/HELLO_ACK field-shape asymmetry: confirmed present, but is *intentional and correctly guarded*, not a bug.** `Hello.1/.2` are lists (`[+ Version]`/`[+ uint]`); `HelloAck.1/.2` are singletons, under the *same field numbers*. The document explicitly calls this out in its own prose ("implementers regularly miss this; TV-001/TV-003 are the byte-level guard") and both TV-001 and TV-003 were hand-decoded and match the CDDL exactly (lists vs. singletons respectively); `map-rs/crates/map-core/src/hello.rs` models it correctly with an explicit citing doc-comment. **Log as consistent** — flagged in the review brief as a suspected ambiguity, but it turns out to be a deliberate, documented, test-vector-anchored design choice.
- **MAJOR (new, found investigating the above) — SessionID prose vs. its own normative test vectors.** See contradiction table row #26.
- **MAJOR — I3 violation in both implementations (crit/ext round-tripping).** See contradiction table row #27.
- **MAJOR — `Hello.cookie` unimplemented in both languages.** See contradiction table row #28.
- **BLOCKING (functional) — `FlowCredit.scope` union not representable in either implementation.** See contradiction table row #29.
- **MINOR — `CapEntry` internal redefinition** (`int` vs `uint`). See contradiction table row #23.
- **MINOR — divergent chain-length numbers surfaced again from the CDDL angle** (8 vs. 5, identity-01 §4 vs §10) — corroborates table row #9 from a different pass.
- **NIT — forward-compat fragility.** Several structs inline `bstr .size 32`/`.size 34` (e.g. `identity-01` §11's `audience` caveat, `pay-01`'s `PayQuote.9`/`PayDispute.5`) instead of referencing the named `TaskID`/`AgentID` types, whose sizes are explicitly open-ended for future post-quantum suites (`AgentID = bstr .size (34..66)`). Harmless today; would need to be hunted down site-by-site if those types ever widen.
- **What wasn't tool-verified:** no CDDL block was run through an actual conformance/parser tool (none available offline) — all verdicts are manual grammar review. Struct-level cross-checks against implementation code covered envelope Body, Hello/HelloAck, and FlowCredit in both languages, and PayQuote/PayAgree/PayInvoice/PayProof/PayReceipt/UsageWatermark in Rust only — identity, discovery, and trust structs, and the Go pay package's structs, were not exhaustively cross-checked field-by-field.

## 4. BCP 14 findings

All 11 drafts read in full (4,041 lines), every capitalized-keyword occurrence traced to source.

- **The "~191 MUST/SHOULD/MAY" figure in the review brief undercounts by roughly 2×.** 191 = exactly `127 MUST` + `64 MUST NOT` (i.e., someone grepped only for `MUST`, which also matches inside every "MUST NOT," and ignored the other nine BCP14 keyword categories). The real deduplicated total across all eleven categories is **≈395**; of that, 110 are the identical 11-keyword front-matter legend repeated verbatim in 10 of 11 docs, and 22 more are boilerplate IETF admin language (draft-expiry / IPR-disclosure sentences), leaving **≈263 genuine protocol-normative usages**. Separately, only 17 lowercase normative-sounding "must/should/may" hits exist family-wide — the family is largely disciplined about capitalization.
- **BLOCKING (structural) — `draft-map-arch-01.md` (Informational) is the sole normative source for at least three real, wire-affecting rules:**
  - Rule Z2 ("no laundering" — a provider MUST NOT forward task content to a higher-numbered zone than received) — cited by `tasks-01` and `ops-01` as "(arch Z1)"/"(arch Z2)" but **never independently restated with normative force in any Standards-track document**.
  - "Intermediate task data MUST be deleted after settlement unless retention is negotiated" (arch §8.2) — a real compliance-relevant obligation that **appears nowhere else in the 11-document family** (not in tasks-01, pay-01, or trust-01).
  - The MAP-Core/Discovery/Tasks/Trust/Pay REQUIRED/RECOMMENDED conformance-class structure (arch §10) — duplicated verbatim in `wire-01` (also Informational), while `ops-01` (the one BCP document) merely *cites* arch §10 rather than stating the requirement itself. Arguably the single most consequential "what must an implementation have to claim conformance" fact in the family, and it lives only in Informational documents.
