Abstract
The Hermes Agent Protocol (HEP) defines a decentralized, capability-aware networking layer for heterogeneous AI inference agents. Unlike identity- or file-centric routing, HEP routes tasks by semantic capability, resource availability, latency, and reputation. Built on a modern stack (QUIC + libp2p Kademlia DHT + Protobuf + gRPC), HEP enables fault-tolerant swarm decomposition, distributed vector memory, and reputation-weighted routing without centralized coordinators. This preprint outlines the architecture, message schemas, routing algorithms, reputation mechanics, and security model to serve as the foundation for an open-source reference implementation.

1. Introduction
Modern AI development is shifting from monolithic cloud inference to heterogeneous, decentralized clusters: local GPUs (BC250, Arc B60), Ollama-hosted models, overflow to APIs (OpenRouter), and IDE-integrated agents. Current orchestration tools lack native capability discovery, weighted routing, and stateful fault recovery across heterogeneous nodes.

HEP addresses this by treating the network as a capability graph. Nodes do not advertise IP addresses; they advertise models, VRAM, latency, trust scores, pricing, and domain expertise. Routing becomes semantic, weighted, and dynamic. Tasks are decomposed into DAGs, dispatched to capable peers, checkpointed for resilience, and merged by a lightweight orchestrator (Hermes).

This specification targets:

Local AI coding clusters and research meshes
IDE-integrated agent workflows (VS Code / OpenCode)
Mixed private/public inference fabrics
Open-source, vendor-neutral deployment
Non-Goals: Centralized cloud orchestration, general-purpose P2P file sharing, blockchain-native tokenomics, model training/fine-tuning pipelines.

Routing Score Formula
When multiple peers respond, the orchestrator computes:

score(p) = 0.35·norm(p.trust.overall)
         + 0.25·norm(1.0 / p.load.avg_latency_ms)
         + 0.20·norm(p.load.tokens_per_sec / 1000.0)

capability_match = 1.0 if tag+domain fully covers task, 0.5 for partial, 0.0 for none
Top-K peers (default K=3) are selected for parallel dispatch or fallback routing

A. Appendix: Routing Pseudocode
def select_next_hop(query, peers):
    scores = {}
    for p in peers:
        if p.trust.overall < query.reputation_floor:
            continue
        if p.load.avg_latency_ms > query.max_latency_ms:
            continue
        if p.pricing.cost_per_million_tokens > query.max_cost_per_token:
            continue
        caps = match_capabilities(query.task_type, p.caps)
        scores[p.node_id] = (
            0.35 * norm(p.trust.overall) +
            0.25 * norm(1.0 / p.load.avg_latency_ms) +
            0.20 * norm(p.load.tokens_per_sec / 1000.0) +
            0.15 * norm(1.0 / p.pricing.cost_per_million_tokens) +
            0.05 * caps
        )
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)[:3]
